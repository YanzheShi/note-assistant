# 个人知识库问答系统 · RAG 双模式评估报告

> 对比对象：**朴素 RAG（naive / RAGChain）** vs **Agentic RAG（agent / LangGraph）**
> 评估日期：2026-08-23　|　评估数据集：内置 10 题（builtin_small）+ 语义缓存演示集（cache_demo_2x2）
> 运行环境：Windows / Ollama（本地 bge-m3 embedding）+ agnes 网关 LLM + ChromaDB（已索引 10547 个 chunk）/ 测试库 `D:\Note\test`

---

## 0. 摘要

本次评估在同一套已索引的知识库、同一份 10 题数据集上，分别跑通 naive 与 agent 两条链路，并额外用一份「重复问法」数据集实测语义缓存命中。核心结论：

- **Token 成本**：Agent 链路总 token 约为 naive 的 **2.96 倍**（prompt token 达 **3.14 倍**），主要因为 agent 每题平均 4.4 次 LLM 调用、且每个节点都带各自 system prompt + 累积上下文。
- **端到端耗时**：两者几乎持平（agent 47.8s vs naive 46.6s，**比值 1.02**）。耗时由网关 RTT + 流式生成主导，而非 token 量，因此调用次数的增加没有线性放大延迟。
- **检索质量**：Agent 显著更好——MRR 0.43 vs 0.34，recall@10 0.50 vs 0.40，NDCG@10 0.374 vs 0.287（agent 借助 query-rewrite / 多轮反思拿到更相关上下文）。详见 §4.1 定量提升。
- **生成质量**：Agent 在 ROUGE-L / 语义相似度上略高（ROUGE-L 0.188 vs 0.149，语义相似度 0.084 vs 0.071），但两者绝对分值都偏低（见 §7 局限性）。
- **语义缓存**：问答级缓存未影响 10 题对比（10 题全唯一、0 命中）；在专门演示集上命中率 50%，可省掉一半 LLM 调用。

|---|---|---|---|

### 2.,3 缓存对耗时的影响（重要说明）

- **语义缓存（问答级）**：agent 报告的 `semantic_cache_stats` 在 10 题 run 中为 `{hits:0, misses:10}`——10 题全唯一、零命中，因此**对该对比的耗时零干扰**，两条链路测的都是完整路径的真实耗时。naive 链路根本不使用语义缓存（`None`）。
- **LLM 网关 token 缓存（prompt caching）**：两边都有 cache_read（naive 3840 / agent 5120 token），它只影响**计费**（按 cache_read 价计费），对墙钟时间几乎无影响，且对称地作用于两条链路，不扭曲对比。
- 结论：本次「耗时 ≈ 持平」的结论**不受缓存干扰**——语义缓存未触发，网关缓存在两边按比例发生。

## 3. 指标定义

| 指标 | 含义 |
|---|---|
| `elapsed_ms` | 单题端到端墙钟耗时（提问进→答案出，实测） |
| `token_usage.prompt_tokens` | 输入 token（含 system + 累积上下文 + 检索内容） |
| `token_usage.completion_tokens` | 输出 token |
| `token_usage.total_tokens` | prompt + completion |
| `token_usage.llm_calls` | 该题触发的 LLM 调用次数 |
| `token_usage.cache_read_tokens` | 命中网关 prompt 缓存、按 cache_read 计费的 token |
| `llm_cache_hit_rate`（顶层） | `cache_read / prompt`，网关 token 级缓存命中率 |
| `semantic_cache_stats` | 问答级语义缓存：{hits, misses, hit_rate} |
| `mrr` / `recall@k` / `ndcg@k` | 检索质量（基于 golden 相关文件是否出现在召回集合） |
| `rouge_l` / `bleu_*` / `semantic_similarity` | 生成质量（系统答案 vs 人工参考答案） |

**关于「@k」的含义**（这是检索指标的核心约定）：`@k` 表示「只看检索返回的前 k 个结果」。
- `recall@k`（召回率@k）：所有应该被召回的相关文档里，有多大比例出现在「前 k 个结果」中——衡量「该找回的找回来没有」。
- `precision@k`（精准度@k）：前 k 个结果里，有多大比例是真正相关的——衡量「翻出来的东西有多少是干货」。
- `ndcg@k`：在「是否相关」之外，额外惩罚「相关结果排得靠后」，更看重排序质量（排在前面的相关项权重更高）。
- `@3 / @5 / @10` 就是分别取前三 / 前五 / 前十名来算。k 越大，召回越容易（recall 走高）、精准越难（precision 走低）；对比时固定同一 k 才有意义。`mrr`（Mean Reciprocal Rank）则只看「第一个相关结果排在第几位」的倒数。

### 4.1 检索质量：agent 相对 naive 的定量提升

下表给出「绝对提升（agent−naive）」与「相对提升（/ naive）」，避免只剩定性「谁优」。

| 检索指标 | naive | agent | 绝对提升 | 相对提升 |
|---|---|---|---|---|
| recall@3 | 0.250 | 0.350 | +0.100 | **+40.0%** |
| recall@5 | 0.400 | 0.500 | +0.100 | +25.0% |
| recall@10 | 0.400 | 0.500 | +0.100 | +25.0% |
| precision@3 | 0.133 | 0.167 | +0.034 | +25.6% |
| precision@5 | 0.120 | 0.160 | +0.040 | +33.3% |
| precision@10 | 0.060 | 0.080 | +0.020 | +33.3% |

> 解读：agent 把召回率稳定在更高水位（recall@10 从 0.40 提到 0.50，相当于每 10 个相关文档多召回 1 个，相对 +25%），同时 precision 同步上行（相对 +25%~33%）——不是靠「召回更多噪声」堆出来的，而是真的更准。NDCG 提升约 30%（+0.087）意味着相关段落排得更靠前，用户/生成器最先看到的片段相关性更强。

## 7. 关键发现与局限性

1. **Token 与耗时解耦**：agent 用 ~3 倍 token 换回了检索质量提升，但端到端耗时基本未变——用户体感延迟不随调用次数线性增长。
2. **检索质量 agent 胜出**：借助 query-rewrite / 反思，agent 召回更相关段落，MRR/recall/NDCG 全面更高。
3. **生成指标偏低属正常**：ROUGE-L / BLEU / 语义相似度是用「开放问答答案」去比「教科书式参考答案」，字面重叠天然偏低，**不能直接等同于答案正确性**。语义相似度（句向量余弦）比 ROUGE 更贴近语义，agent 略优。
4. **检索指标存在数据缺口**：内置集的 `relevant_files` 文件名与当前 test 库部分不匹配，导致 Q1/Q2/Q5/Q8 召回为 0、拖低了整体 MRR。若要严谨评检索，建议按当前库重写 golden 文件。
5. **agent 偶发高成本**：judge/review 触发的反思循环（如第 2 题 8 次调用）是 token 峰值来源，可通过收紧 `need_rewrite` 阈值优化。

---

## 8. 结论与建议

- **选型**：追求低成本、答案直接 → naive 足够（token 仅 1/3）。追求更高召回与相关度、且能接受 3 倍 token 成本 → agent 更优，且延迟几乎不变。
- **成本可控点**：agent 的 token 峰值来自反思循环，调优 judge 阈值即可压制；网关 prompt 缓存已生效（5%~13%），可继续利用。
- **下一步**：① 用当前库重写 golden 文件，得到可信的检索指标；② 若上线「每条问答带 token/时长统计」，基础设施已具备（仅需在 API 层暴露，约 0.5–2.5 天工作量）；③ 引入常驻 naive+agent 同跑对比脚本，调参时一键看账。

## 9. 补充：准确率与置信度为何未评估

### 9.1 准确率（accuracy）接近哪些指标？

原始报告**没有**严格意义的「准确率（答对了没有）」。最接近的代理指标是：

- **语义相似度（semantic_similarity）**：系统答案与人工参考答案的句向量余弦，最贴近「答案像不像参考答案」这一直觉，可作为「软准确率」近似。
- 若要做严格准确率，需要 LLM-as-judge 打分或直接「关键事实命中」规则判定，目前未实现。

注意 BLEU-4≈0 本身就说明：用字面匹配式的「准确率」去评开放问答是失效的——答案用词不同但意思对，会被判错。这也是本评估优先采用语义相似度、而非精确匹配的原因。

### 9.2 置信度（confidence）接近哪些指标？

报告**没有**模型置信度。可采用但未接入的近似来源：

- **token logprobs / 输出概率**：生成层若返回 logprobs，可估算「模型对自己答案的把握」，这是最标准的置信度来源；当前生成链路未捕获。
- 退而求其次，`semantic_similarity` 常被误当成「模型自信程度」，但它衡量的是「与参考的相似」，而非「模型自我把握」，二者不等价。

### 9.3 当时为什么没做这两项？

1. **范围边界**：本次评测框架（设计见 `docs/评测框架扩展方案-多轮+token+缓存命中.md`）的目标是「检索质量 + 生成重叠 + token/缓存成本」三件套；准确率/置信度不在初始 scope。
2. **准确率有成本**：严格准确率需要 judge LLM 或规则判定，会额外烧 token 并引入主观偏差；且 BLEU-4 实测为 0 已证明「字面准确率」对开放问答无意义，故优先用语义相似度。
3. **置信度需改生成链路**：logprob 捕获要在 generator / LLM 调用处改造，且中文语义置信度可靠性一般，投入产出比低，故暂缓。

> 若后续需要，可在 evaluator 增加「LLM-as-judge 准确率」与「logprob 置信度」两个字段——约半天工作量（generator 取 logprobs + evaluator 加判定），重跑即可补齐对比。
