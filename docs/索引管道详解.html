你卡住的 split 属于写侧，where 属于读侧，by 是两者共用的「维度」词。

0. 为什么需要索引

笔记是几千字的长文，LLM 一次塞不下，也没法「按语义」直接翻到相关段落。索引做三件事：

  • 切片：把长文切成 800 字左右的小块（chunk），每块能独立被理解和检索；
  • 向量化：每块转成 1024 维向量，让「意思相近」的块在向量空间里靠得近；
  • 建档：把块的内容、向量、以及一堆描述性字段（来自哪篇笔记、什么标签、在哪个标题下）一起存进 ChromaDB。

最终产物有三个：ChromaDB 向量库 ParentDocstore 父块库（仅 v2b） sync.db 增量状态。后面所有检索、问答都建立在它们之上。

3. Stage 2 · RichPreprocessor：保护富结构

文件 indexing/preprocessor.py。这一步最容易被忽略，但很重要。

为什么要先抽走代码块/表格/mermaid/图片？

4. Stage 3 · Splitter：切分（核心，回应 split / by）

4.1 split 到底是什么

split = 把一篇长笔记切成若干小块（Chunk），每块能被单独 embed、单独检索。代码在 indexing/splitter.py。

两层 splitter（make_splitters() L22），理解成两刀：
  • 第一刀 · split by heading：MarkdownHeaderTextSplitter 按标题层级切（#/##/###/####，见 L14 _HEADER_CONFIG）。切完每块自动带上它所属的 h1~h4 信息。
  • 第二刀 · split by character：RecursiveCharacterTextSplitter 按字符递归细切（L43）。chunk_size=800、chunk_overlap=150，separators=["\n\n","\n","。"," ",""]（L36，中文句号 。 在空格之前，这是中文切分的关键）。
记忆口诀：先 by heading 切大块，再 by character 切小块。

4.2 heading_path 怎么拼出来

第一刀切完，每块已经知道自己的 h1~h4。第二刀细切后，split_v2()（L139-142）把 h1~h4 拼成一条路径字符串：

hp_parts = [meta.get(k) for k in ["h1","h2","h3","h4"]]
hp = " > ".join(p for p in hp_parts if p) or "无标题"

# 我们的例子笔记，## 二、关键设计点 > ### 2.1 混合检索 这一块：
#   h1="检索技术综述", h2="二、关键设计点", h3="2.1 混合检索"
#   → heading_path = "检索技术综述 > 二、关键设计点 > 2.1 混合检索"

heading_path 极为重要：它是后面「结构优先级 boost」和「图片邻居扩展」的依据（P3/P4 会用到）。

4.3 「by」这个词在本项目的两层含义

含义 A —— 切分的依据：split by heading / split by character。指「按什么维度把文本切开」。

含义 B —— 组织和过滤的维度：每个 chunk 的 metadata 里都写着 filepath / title / tags / dir / heading_path。检索时就能「按 filepath 过滤」「按 tags 过滤」。

关键：by 的维度在索引时（写侧）就已经写进每条 chunk 的 metadata 了——这是连接写侧和读侧的桥梁，见 4.6 / 6.3。

4.4 v1 / v2 / v2b 三种策略

策略切分方式heading_path存储
v1纯 Recursive无单层进 ChromaDB
v2header + recursive有单层进 ChromaDB
v2b（本部署）header + recursive有父子双存（见下）

4.5 v2b 父子双存（本部署用的策略）

split_v2b()（L224）产出两类 chunk：

类型去向作用是否 embed
child（≤800字细块）ChromaDB负责检索命中✅ 嵌入
parent（整节粗块 ≤parent_chunk_size）ParentDocstore命中后回退整节喂给 LLM❌ 不嵌入
为什么 parent 不 embed、不进 ChromaDB？
① 省成本：整节太长，嵌入意义不大；② 检索用细块更准；③ 命中 child 后，靠 parent_id 从 docstore 取回整节，既能精准命中、又能给 LLM 完整上下文。两者靠 parent_id 关联（L286 / L299）。 
# split_v2b 产出的关联（L285-303）
pid = "AI_检索技术.md::parent::0"   # 注意 / 被换成 _，但保留整体不冲突
parents.append(Chunk(page_content="整节正文", metadata={"parent_id":pid, "kind":"parent", ...}))
children.append(Chunk(page_content="某 800字片段", metadata={"parent_id":pid, "kind":"text", ...}))
# 检索命中 child → 用 child.metadata["parent_id"] 去 docstore 取 parent 整节

5. Stage 4 · Embedder：文本→向量

indexing/embedder.py 的 OllamaEmbedder.embed()：调用本地 Ollama 的 bge-m3 模型，把每个 chunk 的 page_content 转成 1024 维向量。一个 chunk → 一条向量。

6. Stage 5 · Ingestor：编排 + 入库（回应 where）

indexing/ingestor.py 是写侧的总指挥。index_vault()（L121）对每篇笔记走 6 步：

# index_vault 主循环（L149-230）逐笔记：
for node in docs:
    dir_ = 该笔记相对 vault 的父目录
    cleaned, fm_chunks = preprocessor.process_with_meta(node)   # ① 抽富结构
    node_for_split = replace(node, raw_md=cleaned)              # 切分吃清洗后文本
    chunks = split_v2b(node_for_split, hs, cs)                  # ② 切分（本部署 v2b）
    chunks = preprocessor.restore(chunks)                       # ③ 还原占位符 + 写 has_*
    for c in chunks:                                      # ④ 补 metadata + 拼结构前缀
        c.metadata["filepath"]=node.filepath
        c.metadata["tags"]=node.tags
        prefix = build_structural_prefix(node, c.metadata, dir_)
        c.page_content = f"{prefix}\n\n{c.page_content}"         # 机制A：前缀进正文
    docstore.add(parent_id, text, meta)                         # ⑤ v2b 父块进 docstore
    self.upsert(all_chunks)                                     # ⑥ 入库 ChromaDB

6.1 结构前缀（机制 A，L15）

build_structural_prefix() 拼出 目录 › 《文档名》› 标题路径，直接写进 page_content 头部：

# 例子笔记某 chunk 入库前长这样：
AI › 《检索技术综述》› 二、关键设计点 > 2.1 混合检索

稠密 + 稀疏（BM25）融合，兼顾语义与关键词。……
为什么前缀进正文而不是只放 metadata？因为 dense 向量、BM25 关键词、reranker 三处都靠正文感知层级——放 metadata 只有 where 过滤能用，放正文三处都受益。

6.2 metadata 里写了哪些字段（这是 where 的弹药）

每个 chunk 入库时，metadata 至少包含：

字段含义谁会用到
filepath来自哪篇笔记where 按文件过滤
title文档标题展示 / 过滤
dir所在目录where 按目录过滤
tags标签列表where 按标签过滤
wikilinks双链图谱扩展
heading_path标题路径结构 boost / 展示
kind / parent_id块类型 / 父块 idv2b 父子关联
has_code 等含富结构过滤 / 展示
ChromaDB 对 metadata 有洁癖：空列表、空字符串、list 元素类型不一都会拒绝。upsert()（L85-97）会清洗：空列表跳过、空串跳过、list 元素统一转 str。这就是为什么 front matter 里 tags: [2026] 这种整数会被转成 "2026"。

6.3 upsert：生成 ID + embedding + 入库

ids = [f"{filepath}::{index}::{kind}" ...]   # _make_id L57，保留 / 不归一
embeddings = embedder.embed([c.page_content ...])
collection.upsert(ids=ids, documents=docs, embeddings=embeddings, metadatas=metadatas)
ID 为什么保留 /？（L57-63）若把 a/b.md 的 / 也换成 _，会和 a_b.md 生成同一 ID，导致 chunk 静默互相覆盖、数据丢失。ID 对 ChromaDB 是透明字符串，保留 / 无副作用。

6.4 where 这个词到底指什么（回应你最大的卡点）

where 是 ChromaDB 的查询参数，在检索期（读侧 / P3）才真正执行，不在索引期。

# 检索时的典型调用（P3 你会看到）：
collection.query(
    query_embeddings=[question_vec],
    where={"filepath": "AI/检索技术.md"},   # ← where：只查这一篇笔记
    n_results=5,
)

它能过滤的字段 = 索引时写进 metadata 的那些（filepath / tags / dir / heading_path …）。

前后逻辑一句话：索引时「埋」好 metadata 字段（by 维度）→ 检索时 where 用这些字段过滤 → 再按向量相似度排序。

7. 增量索引：sync.db 与 autoindex

  • 全量索引：index_vault(wipe=True) 清空重建，慢但彻底。
  • 增量索引：sync.py 的 SyncDB 给每个文件记 mtime + sha256 双重指纹。need_reindex()（L72）两者任一变化才重索引——只改了访问时间（mtime）但内容没变（sha256 同）不会白跑。
  • 为什么要全量结尾刷新 sync.db（ingestor L241）：否则下次增量会把全库当「新文件」重跑一遍。
  • autoindex：autoindex.py 用 watchfiles 监听文件变动 + 防抖 + 单飞队列（asyncio.Lock），保证同一时刻只有一个 worker 写 ChromaDB / 调 Ollama，杜绝并发写崩库。每累计 autoindex_full_sync_every（默认 20）次增量，触发一次全量校准（重建 BM25 + WikiGraph + docstore）。

补充 · 图片处理全链路（你漏看的那块）

为什么前面没讲图片？① 例子笔记《AI/检索技术综述.md》没有任何图片；② image_understand_enabled 默认 False（G6 零回归，开关在 config.py），本部署靠 .env.local 钉 True 才生效；③ 还需本地图片 + VLM 可用。所以它是一条「条件开启的高级特性」，但链路完整、是生产路径。

A. 索引时：图片怎么进库

  • ① 抽取（preprocessor.py::_extract_images L344）：扫描 ![[embed]] / ![alt](path)，抽成 IMAGE_UID_* 占位符（和代码/表格同机制，保护不被切碎）。raw 存完整 markdown 语法，meta 存 src/alt。
  • ② 理解（ingestor.py L140 注入 make_image_enricher，来自 understanding.py）：对每张图分级路由——decorative（logo/小图标）跳过不调 VLM；use_svg 走 SVG 原生解析（零 VLM）；need_vlm 调 VLM 产出结构化 8 字段（image_type / title / summary_short / description / ocr_text / entities / data_points / mermaid_equivalent）。
  • ③ 入库（generate_summaries L199-213）：给图片生成一条 summary chunk，metadata 带 image_description / image_ocr_text / asset_id / img_url / render_hint / trust；其 page_content 是「图片理解：标题+描述+OCR+实体」这段文本，这段话被 embed 进 ChromaDB —— 图片因此能被语义检索命中。

B. 检索时：怎么「检索出图片」（P4 预告）

  • 图片 summary chunk 和普通文字 chunk 一起参与向量检索；用户问到图片相关内容 → 命中该图片 chunk。
  • pipeline/image_answer.py::_is_image_chunk 识别图片 chunk（kind=="image" 或 asset_id+描述字段）。
  • expand_image_neighbors 做邻居扩展（补回图片附近文字块上下文）。
  • image_answer.py 用 asset_id / img_url 把 [[IMG:]] 渲染成真实图片返回。
本质一句话：【以文检图 + 以 ID 取图】。图片不是像素级检索，而是先把图片「文字化」（VLM 描述 + OCR），文字进向量库参与语义检索；命中后用 asset_id 把原图取出来渲染。这就是为什么索引管道里看不到「图片库」——图片和文字是混在同一个 ChromaDB 里靠 metadata 的 kind 区分的。

图片从笔记到被检索出来的完整链路：先文字化进向量库，命中后再取原图。
