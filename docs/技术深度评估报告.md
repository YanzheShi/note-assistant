# 技术深度评估报告

> 评估日期：2026-07-14
> 评估视角：从算法设计、架构决策、技术深度出发，而非工程基建角度

---

## 一、总体判断

这个项目最大的问题是：**没有一个真正"硬核"的技术亮点。**

目前的状态是"把成熟的库拼起来，加了一点自己的适配逻辑"。这在个人项目中完全没问题，但如果要以技术深度来展示——目前还不够。以下是逐模块分析。

---

## 二、各模块技术深度评审

### 2.1 Preprocessor（富结构预处理）⭐⭐⭐⭐

**这是整个项目中最有技术含量的模块，也是唯一一个真正"自己做"而非"调库"的部分。**

**做了什么：**

```
提取阶段（process）
  代码块 → UUID占位符 → ExtractedChunk
  表格   → UUID占位符 → ExtractedChunk
  Mermaid → UUID占位符 → ExtractedChunk
  图片   → UUID占位符 → ExtractedChunk
       ↓
  切分（在"干净的"文本上切块）
       ↓
还原阶段（restore）
  将占位符还原为原始富结构
       ↓
生成摘要（generate_summaries）
  为每个富结构生成自然语言描述
  "表格（约5列）: ..."
  "Mermaid graph 图: ..."
  这些摘要也被索引，保证富结构可检索
```

**技术亮点：**

- 正确处理了处理顺序：代码块保护跑在最前面，避免 `MarkdownHeaderTextSplitter` 被代码块里的 `#` 干扰
- 占位符策略避免了切分器破坏富结构
- 摘要生成让表格/图表也能参与语义检索，这是很多 RAG 项目忽略的点

**不足之处：**

- 占位符是简单的 UUID 字符串，切分后如果 UUID 落到 chunk 边界上怎么处理？没看到明确的边界保护
- 摘要用的是非常简单的模板拼接，不是真正"理解"富结构内容

---

### 2.2 Splitter（切分策略）⭐⭐

**现状：基本上是 LangChain 的 MarkdownHeaderTextSplitter + RecursiveCharacterTextSplitter 的薄封装。**

**自己做了的事：**

- `heading_path` 拼接逻辑：`" > ".join(p for p in parts if p)` —— 过滤空的 h1，因为 Obsidian 笔记通常从 `##` 起始。这是一个小但真实的设计决策
- `docnode_to_lc_doc` 适配器：把项目的 `DocNode` 转成 LangChain 的 `Document`，并注意 ChromaDB 不支持嵌套 metadata

**LangChain 帮你做的事（即你没有自研的）：**

- 标题层级切分 → `MarkdownHeaderTextSplitter`
- 递归字符切分 → `RecursiveCharacterTextSplitter`
- 重叠窗口 → 参数 `chunk_overlap`

**关键缺失：**

```
split_v2b() → raise NotImplementedError  ← 父子块层级关系
split_v3()  → raise NotImplementedError  ← 块级别 wikilink 注入
```

这两个才是真正能体现技术深度的功能：
- **v2b（层级关系）**：当前每个 chunk 是扁平的，不知道自己是"父"还是"子"。后期检索时如果能返回"命中 chunk 的父级标题路径"，结构化展示能力会大幅提升。
- **v3（wikilink 注入）**：chunk 级别的 wikilink 展开——如果 chunk A 提到 `[[概念B]]`，就把概念 B 的内容摘要也注入 A 的索引。这个才能真正打通"双链→检索"的闭环，而不只是事后用图扩展（见下文）。

**还有个低级问题：**

`split_v2()` 里残留了 `print()` 调试语句，生产代码不应该有。

---

### 2.3 检索模块（Hybrid + BM25 + Reranker）⭐⭐

**混合检索：做了，但实现较浅。**

**做了什么：**

- Dense（ChromaDB 向量搜索）+ Sparse（BM25 关键词搜索）并行检索
- Min-max 归一化后加权融合（alpha 可调）
- 融合结果送入 BGE-Reranker-V2-M3 精排

**实质技术含量分析：**

1. **混合检索算法**：就是最基础的 min-max 归一化 + 线性加权。学术界/工业界有大量更优的融合策略：RRF（Reciprocal Rank Fusion）、加权 RRF、基于学习-to-rank 的融合……但 min-max 确实也够用，不算缺点，只是没有亮点。

2. **BM25 实现**：直接用的 `rank-bm25` 库，`jieba` 分词。没有自己实现 BM25 算法，也没有针对中文做特殊优化。pickle 持久化是正确的做法。

3. **Reranker**：FlagEmbedding 的 `FlagReranker`，标准调用。有一点值得提——做了 `transformers` 兼容层的 monkey-patch 来处理 Windows 上的路径问题，这是工程实践的体现。

**不足：**

- BM25 索引是在初始化时一次性构建的，增量索引时不会自动重建。DECISIONS.md 里记录了这个问题但没解决。这意味着增量索引后 BM25 检索结果是旧的——混合检索实际上退化为纯 dense 检索。
- 混合检索没有做任何召回结果的去重策略（同一个 chunk 可能同时被 dense 和 sparse 召回，虽然融合加权会处理分数，但 ID 级别的去重更干净）。

---

### 2.4 Query Rewrite（查询改写）⭐

**现状：用 LLM 把口语问题转陈述句，prompt 写死代码里。**

```
用户问  →  为什么比特币会涨
    ↓
LLM改写  →  比特币价格上涨的原因
    ↓
用改写后的语句做检索
```

**技术含量很低：**

这本质上就是一次 LLM 调用，prompt 是固定的。学术界对 Query Rewrite 的探索很多：
- 伪相关反馈（PRF）：用第一轮检索结果来扩展 query
- HyDE：先生成假设答案，用答案做检索
- 多轮改写：结合对话历史改写指代（"那第二个呢"→"比特币的第二个上涨原因"）
- 子问题分解：复杂问题拆成多个子问题分别检索

你目前的多轮对话中，query rewrite 并没有结合历史上下文——这是最大的遗漏。比如连续对话中用户说"那第二个原因呢"，改写后的 query 仍然是"那第二个原因呢"，不会展开为"比特币价格上涨的第二个原因"。

---

### 2.5 Graph（双链知识图谱）⭐⭐⭐

**理念很好，但实现深度不够。**

**做了什么：**

- 解析 vault 中所有 `[[wikilink]]`
- NetworkX 构建有向图
- 检索时 BFS 一跳扩展：从命中 chunk 的源笔记出发，把双链关联的邻居笔记也纳入检索结果
- Decay score 衰减（邻居节点的分数打折扣）

**这是项目的一个差异化亮点**——利用 Obsidian 特有的双向链接结构做语义扩展。通用 RAG 没有这个能力。

**但深度不足：**

1. **只有一跳 BFS**：没有考虑多跳推理路径。A → B → C 的间接关联完全丢失了。对于知识图谱真正有价值的"长链推理"场景，一跳不够。

2. **只有结构化链接，没有内容关联**：wikilink 是用户手动创建的链接。如果两篇笔记语义高度相关但不存在 wikilink，图扩展完全找不到。这里应该加入语义相似度边作为补充。

3. **图是静态的**：增量索引后，图不会自动更新。新增的笔记和 wikilink 在图里不存在。

4. **一篇文章的所有 chunk 共享同一个邻居扩展**：这太粗粒度了。理想情况是：哪个 chunk 命中了 `[[target]]` 链接，才把 target 笔记的内容拉进来。否则引入很多噪音。

5. **GraphRAG 的误解**：你目前的实现是"检索后图扩展"，而不是真正的 GraphRAG。真正的 GraphRAG 是微软提出的方案——在图层面做社区检测、生成摘要，再把这些摘要作为检索的语境。你做的其实是 graph-enhanced retrieval，不是 GraphRAG。命名上不要混淆。

---

### 2.6 Generation（答案生成）⭐⭐

**现状：标准的 RAG prompt + 多轮历史拼接。没有技术亮点。**

**做了什么：**

- 双 LLM 实例（普通 + 流式分别创建）
- 上下文格式化：把 RetrievalResult 转为 LLM 可读文本
- 多轮历史：最近 10 轮对话
- 流式输出 SSE

**不足：**

- **引用标注缺失**：生成的答案里没有引用来源的具体位置。这是 RAG 最基本的可信度要求——用户看到答案，想知道"这句话是从哪个笔记来的"。理想状态是 `答案文本 [1] 答案文本 [2]`，底部列出引用来源。
- **没有 self-reflection**：生成结果后没有检查"这个答案是否真的被检索到的内容支撑"。幻觉检测完全靠 prompt 约束，没有二次验证。
- **上下文格式化过于简单**：就是拼字符串。没有做 chunk 的排序、去重、冗余压缩。10 个 chunk 如果内容高度重复，会浪费 context window。
- **System prompt 硬编码**：没有模板化，不可配置，不支持不同场景使用不同的 prompt。

---

### 2.7 Pipeline（RAG 管线编排）⭐⭐

**现状：串联了所有组件，但编排逻辑比较简单。**

**做了什么：**

- 检索路由：先判断是否需要查知识库（"今天天气"→不需要，"比特币原理"→需要）
- 顺序管线：Rewrite → Hybrid Search → Rerank → Graph Expand → Generate
- 支持 trace 模式：每一步输出中间结果

**问题：**

- **路由判断也是用 LLM**：多了一次 LLM 调用，增加了延迟。实际上简单的关键词匹配就能处理大部分"不需要检索"的场景（问候、闲聊、天气等）。
- **管线是严格的同步串行**：Rewrite → Search → Rerank → Graph → Generate，每一步都等前一步完成。虽然有 trace 模式展示各步骤，但没有真正的并行化。
- **没有自适应策略**：不管检索质量如何，一律走完整管线。如果前 3 个结果的分数已经很高，Rerank 和 Graph Expand 是否还有必要？

---

### 2.8 Evaluation（评测体系）⭐⭐⭐⭐

**这是另一个有技术含量的模块。自己手写了完整的检索和生成指标。**

**做了什么：**

- 检索指标：Recall@K、Precision@K、MRR、nDCG@K，全部手写
- 生成指标：ROUGE-L（LCS DP 算法手写）、BLEU（brevity penalty 完整实现）、语义相似度（embedding 余弦 + Jaccard 回退）
- RAGAS 集成：faithfulness / context_precision / context_recall
- Evaluator 编排器：批量跑 + 单条调试
- 内置 10 条评测问题，覆盖各组件

**亮点：**

- ROUGE-L 的 LCS 算法是自己用 DP 写的，不是调库
- BLEU 的 brevity penalty 是公式级正确实现
- 路径归一化：短文件名匹配（不依赖绝对路径）
- 评测问题设计有针对性，覆盖了 RAG 各组件

**不足：**

- **没有消融实验**：评测只跑完整管线，没有逐个关闭组件对比。"关掉 Rerank 后 Recall@10 下降多少？""关掉 Graph Expand 后生成质量如何变化？"这些数据才能真正证明每个组件的价值。目前只能说明"整体还行"，不能说明"哪个组件起了多大作用"。
- **数据集只有 10 条**：太少，统计显著性和泛化能力不足。
- **Faithfulness 用的是 LLM 判断**：这本身没问题，但没有和人工标注做一致性校验。LLM 判断 faithfulness 的准确率是多少？不知道。
- **没有线上评测闭环**：用户对答案的反馈（点赞/点踩/追问/复制）没有收集，无法做 A/B 测试和持续优化。

## 三、整体架构的深层问题

### 3.1 什么是"薄封装"，什么是"自研"

把项目拆开来看，真正自己做的部分：

| 组件 | 自研程度 | 说明 |
|------|----------|------|
| Preprocessor | 🟢 100% 自研 | 占位符提取/还原/摘要生成全手写 |
| Splitter | 🟡 20% 自研 | heading_path 拼接是自研的，其余是 LangChain |
| Spare Retriever | 🟡 10% 自研 | jieba 分词 + rank-bm25 库，自己只做了 ChromaDB 适配 |
| Dense Retriever | 🟡 5% 自研 | 完全依赖 ChromaDB |
| Hybrid Retriever | 🟡 30% 自研 | min-max 归一化 + 加权融合逻辑自写 |
| Reranker | 🟡 10% 自研 | 调 FlagEmbedding，加了 Windows 兼容层 |
| Query Rewrite | 🟡 10% 自研 | LLM 调用，prompt 硬编码 |
| Graph | 🟢 80% 自研 | NetworkX 建图 + BFS 扩展 + decay score 逻辑自写 |
| Generator | 🟡 20% 自研 | LLM 调用 + 上下文格式化 |
| Pipeline | 🟢 60% 自研 | 路由 + 编排逻辑自写 |
| Evaluation | 🟢 90% 自研 | ROUGE-L/BLEU/MRR/nDCG 全手写 |

**核心发现：这个项目最大量的代码是在"胶水层"——把 LangChain、ChromaDB、FlagEmbedding、rank-bm25、NetworkX 这些库串起来。真正从零实现的算法很少。**

这不是问题，大部分 RAG 项目都是这样。但要意识到：如果面试官问"你做了什么"，你能说的技术亮点是：
1. 富结构预处理管线（preprocessor）
2. 双链图扩展检索（graph）
3. 手写评测指标（evaluation）

其他就只是"我用过 LangChain / ChromaDB / FlagEmbedding"的程度。

---

### 3.2 关于 Graph 的过誉风险

你一直在强调"GraphRAG"是亮点，但需要注意：

**你的实现 vs 真正的 GraphRAG：**

| 维度 | 你的实现 | 微软 GraphRAG |
|------|----------|---------------|
| 图结构 | wikilink 有向图 | 实体-关系-实体 |
| 图构建 | 解析 `[[link]]` 语法 | LLM 抽取实体和关系 |
| 图使用 | BFS 一跳扩展 chunk | 社区检测 → 社区摘要 → 检索摘要 |
| 技术门槛 | 低（正则 + BFS） | 高（社区检测算法、多轮 LLM 调用） |

文档和命名里不要过度使用"GraphRAG"这个词。你的方案应该叫"wiki-link enhanced retrieval"或"双链图增强检索"。

---

### 3.3 为什么"胶水代码"不是缺点，但也不够

RAG 领域 80% 的工程工作确实是集成和适配。但区分"好项目"和"普通项目"的关键在于：

**普通项目：** "我把 A、B、C 三个库串起来，能跑通了。"

**好项目：** "我把 A、B、C 串起来，并且在连接点做了以下优化：....."

你的项目在 preprocessor 和 graph 模块做到了"好项目"的标准。但 splitter、hybrid、generator 还停留在"能跑通"。

---

## 四、技术深度改造建议

以下不是跑 CI/CD 装 Docker 那种"添砖加瓦"，而是真正提升技术深度的方向：

### 4.1 让 RAG 真正"智能"

**自适应检索策略（Adaptive RAG）：**

当前管线是固定的：Rewrite → Search → Rerank → Graph → Generate。不管什么问题都走一遍。

改成自适应的：
- 简单问题（"比特币是什么"）→ 直接 dense search + generate，跳过后面的 rerank 和 graph
- 需要关联的问题（"比特币和以太坊的区别"）→ 走 graph expand
- 需要精度的问题 → 走 rerank

判断"问题难度"的方法：LLM as judge、检索分数方差、query 长度等。

### 4.2 让检索真正"懂你"

**多轮对话感知的 Query Rewrite：**

当前 rewrite 只看当前 query，不看历史。改成：

```
User: 比特币为什么会涨
Assistant: [答案...]
User: 那第二个原因呢

当前 rewrite: "那第二个原因呢" → "那第二个原因呢" （没变！）
正确 rewrite: "那第二个原因呢" → "比特币价格上涨的第二个原因" （结合上下文展开指代）
```

这是多轮 RAG 最基础也最重要的一步。

### 4.3 让 Graph 真正"有用"

**内容关联边（不只是 wikilink）：**

```
当前图：A --[[link]]--> B   （只有用户手动创建的链接）

增强图：A --[[link]]--> B
        A --semantic--> C   （embedding 余弦相似度 > 0.85）
        A --keyword--> D    （共享 N 个关键词）
```

这样即使没有 wikilink 的笔记也能被关联起来。

**Chunk 级别而不是文档级别：**

```
当前：文档 A 的任何一个 chunk 命中 → 把文档 B 全部加入

改进：文档 A 的 chunk_3 命中了 [[B]] → 只把文档 B 中和 chunk_3 语义最相关的 2 个 chunk 加入
```

---

### 4.4 让生成真正"可信"

**引用标注（Citation）：**

```
当前：答案是一段纯文本，用户不知道来源

目标：
比特币价格上涨主要有三个原因 [1]:
1. 供需关系 [2]
...

参考文献：
[1] 经济学笔记.md, 第5段
[2] 比特币分析.md, 第2段
```

**幻觉检测（Self-Reflection）：**

生成答案后，让 LLM 反向检查："答案中的每个陈述，是否都能在检索到的上下文中找到依据？"不符合的打标记或删除。

### 4.5 让评测真正"证明价值"

**消融实验（Ablation Study）：**

当前评测只能说明"整体怎样"，不能说明"哪个组件贡献了多少"。

| 配置 | Recall@10 | 生成质量 |
|------|-----------|----------|
| Dense only | ? | ? |
| Dense + Sparse (Hybrid) | ? | ? |
| Hybrid + Rerank | ? | ? |
| Hybrid + Rerank + Graph | ? | ? |
| Full + Rewrite | ? | ? |

没有这张表，你就不知道 graph expand 是真的有用还是一个"装饰品"。

## 五、真正的技术亮点总结

**如果要把这个项目写到简历上或拿去面试，可以这样提炼：**

1. **富结构感知的文档预处理管线**：自研的占位符替换 + 还原机制，让代码块/表格/Mermaid 图在切分过程中不被破坏，并生成结构化摘要保证可检索。这是 LangChain 原生不提供的功能。

2. **双链图增强检索**：利用 Obsidian 特有的 `[[wikilink]]` 双向链接构建知识图谱，通过 BFS 扩展 + decay 机制将关联笔记纳入检索范围，突破纯语义检索的信息边界。

3. **手写评测体系**：完整实现了 ROUGE-L（LCS DP）、BLEU（含 brevity penalty）、MRR、nDCG 等指标，具备消融实验的单组件开关能力（待实现）。

**这三个是你和别的"用过 LangChain 做过 RAG 的人"的差别。**

---

## 六、一句话

> 项目的胶水层做得扎实，preprocessor 和 graph 两个模块有一定独创性，评测体系手写体现了扎实的算法功底。但 splitter 是薄封装，检索没有自适应策略，图扩展深度不够，生成缺乏引用标注和幻觉检测。要做技术深度的提升，应该聚焦在：自适应检索路由、多轮 Query 改写、内容关联边的图扩展、引用标注 + 幻觉检测、以及消融实验这五个方向。
