# 层级检索与结构优先设计方案

> 状态：✅ 已实现（两阶段一起上）| 日期：2026-07-28 | 关联：`splitter.py` · `ingestor.py` · `retrieval/hybrid.py` · `retrieval/structural.py`

## 一、背景与问题

用户的原始诉求（2026-07-28）：

> 一个文档标题是「Code Agent 架构」，里面有个一级标题「二、关键设计点」。当我问
> "Code Agent 架构的关键设计点是什么？"时，这种「文档名 + 标题 + 分级标题」的连接，
> 现在能被检索到吗？

换句话说：**Obsidian 笔记天然是「文件夹嵌套 → 文档 → 多级标题」的层级结构，用户提问也常以
"哪篇 / 哪章"为锚点。当前检索链路是否把这条层级路径当成一条可匹配的整体？**

结论：**当前没有接上。** `heading_path` 算出来了，但只停在元数据里，没进入可被检索的文本。



遇到问题就是，当我问一个有了这个层级的问题的时候， 没有精确找到这个层级的所有内容，反而找到另一个总结的不够细的但是段落中有这个标题的文档块，导致回答不详细，不完整。

### 实证（当前代码）

| 位置 | 代码事实 | 后果 |
|---|---|---|
| `indexing/splitter.py` → `split_v2()` | 计算 `heading_path`（如 `Code Agent 架构 > 二、关键设计点`），写入 chunk 的 `metadata` | 结构已解析，但**仅存元数据** |
| `indexing/ingestor.py` 第 55–56 行 | `embeddings = embed([c.page_content …])`、`documents = [c.page_content …]` | 入库文本**只有正文**，标题路径没拼进去 |
| `retrieval/hybrid.py` 第 211 行 | `final = α·dense + (1−α)·sparse`，`α = dense_weight = 0.7` | 融合只吃 `page_content`，与结构元数据无关 |
| `retrieval/hybrid.py` 第 146–164 行 `filtered_search()` | 支持按 `heading_path` / `filepath` 元数据过滤 | 但 agent 默认 `hybrid_search()` **不传** `heading`，仅用于人工指定过滤 |
| `retrieval/reranker.py` | 交叉编码只吃 `page_content`（正文） | 同上，结构不参与精排 |

因此，问「Code Agent 架构的关键设计点」，query 里的「Code Agent 架构」「关键设计点」这两个
**结构锚点**在正文里多半不出现 → dense 只能靠语义近似、BM25 基本匹配不到 → 默认链路下大概率
召回不到目标段。`heading_path` 现在是"死"的：只用于检索后给 LLM 展示来源路径（`_format_results`）。

## 二、设计目标

1. **层级连接可被检索**：文档名、标题、分级标题（h2→h3→…→末级）与正文融合成一条可检索文本。
2. **结构优先级高于纯内容**（用户明确要求"高一点"）：当 query 命中某段的文档名/章节名时，
   该段稳定靠前，但不至于完全盖掉内容相关性。
3. **零回归 / 纯叠加**：不换模型、不改向量 schema、不破坏现有 `filtered_search` 与引用展示。

## 三、核心思路：两个互补机制

层级优先由**两层**共同实现，作用在不同阶段，互不冲突：

| 机制 | 作用层 | 解决什么 |
|---|---|---|
| **A. 结构前缀拼进 `page_content`** | 语义/向量层（embedding + BM25 分词 + reranker） | 让向量空间"感知"到结构上下文 |
| **B. 结构分 `β` 叠加到排序分** | 排序层（`_merge_results`） | 显式给结构加权，**不污染正文语义**，且只吃元数据 |

二者叠加 = dense 有结构上下文 + 排序有结构 boost = 用户要的"层级优先"。纯内容类 query
（没提文档名/章节）结构分≈0，只剩 dense+sparse，与现状一致。

### 机制 A：结构前缀（语义层）

入库文本由

```
{正文}
```

变为

```
{层级目录} › 《{文档名}》› {标题 h1} › {分级标题 h2 › h3 › …末级}

{正文（restore 后的最终正文）}
```

对应示例，入库文本为：

```
AI/Agents › 《Code Agent 架构》› 一、背景 › 二、关键设计点

关键设计点的三条原则是……
```

- **层级目录**：从 `node.filepath` 取 vault 内相对父目录（如 `AI/Agents`）。**需新增 `dir` 元数据字段。**
- **文档名**：`node.title`（front matter 或文件名兜底）。
- **标题 + 分级标题**：即现有 `heading_path`（`h1 > h2 > …`），天然拼到末级；某笔记 `##` 起手无 h1 时，前缀自动少 h1 一级，合理。
- 四层用 `›` 串成 breadcrumb，前置到正文，再空一行接正文。

> 收益：dense / BM25 / reranker 三处**自动吃到**结构上下文（因为它们都消费 `page_content`）。
> 代价：前缀进 embedding 略稀释纯正文语义，笔记 RAG 里通常净赚；LLM 看到的片段同时有前缀和
> 引用里的标题路径，略冗余但无害。

### 机制 B：结构分 `β` 叠加（排序层）

把结构信号**单独抽成一路分数**，叠在 dense+sparse 之上，用旋钮 `β` 控制优先级。
结构字段基本现成（`title` / `heading_path` / 新增 `dir` 均在元数据），**不依赖重 embedding**。

`structural_score(query, meta)` 算法：

1. query 用 jieba 分词（BM25 已用 jieba，无新依赖）。
2. 统计 token 落在 `{dir, title, heading_path}` 上的比例，归一化到 `[0, 1]`。
3. **强信号**：query 命中某段 `title` 或 `heading_path`（如问"Code Agent 架构"命中文档名）→ 结构分高。
4. **弱信号**：只命中 `dir` 目录名 → 结构分较低。

**硬兜底（title 精确命中）**：query 中出现与某段 `title` 完全一致的片段（标点归一，去《》与空格），
直接判"结构强命中"，追加固定 bonus（默认 `+0.15`）。保证用户明显在问"某篇/某章"时该段铁定顶上来。

最终融合公式（在 `hybrid.py` 第 211 行附近扩展）：

```
final = α·dense + (1−α)·sparse + β·structural      (structural > structural_min_score 时才施加，否则忽略)
```

- `β` 默认取 **0.25**（"高一点"的具象值）：结构命中段比纯正文段多出一个 β 增量，稳定靠前，
  但不至于"提了文档名就一票否决正文相关性"。`β=0` 时完全退化回现状，零回归。
- **防错边界**：`β` 过大易"提到文档名就排前、哪怕正文不相关"。故仅在 `structural > structural_min_score`
  （建议 0.5）时才施加 boost，低分直接忽略，用噪声换不翻车。

> reranker **不动**：它已在 `page_content` 上吃到机制 A 的前缀红利；机制 B 只在融合层加分，
> 不进交叉编码，避免双重加权。

## 五、落地策略（分两阶段，便于量化评估）

- **阶段一**：仅上「机制 A 前缀拼进正文 + 重索引」。先让 dense/BM25/reranker 在语义层感知结构。
  改动最小，立刻能测「Code Agent 架构的关键设计点」能否召回。
- **阶段二**：再加「机制 B `structural_score` 第三路 + β 旋钮」。用评测（`--ragas`）对比阶段一与
  现状的 recall / ndcg，调 `β`。

这样每一刀的效果都能量化，不会一口气改完不知道哪步起作用。

## 七、风险与权衡

- **前缀稀释语义**：结构词进 embedding 略冲淡纯正文语义，笔记 RAG 场景通常净赚；若实测退化可调前缀权重或长度。
- **β 过大翻车**：已用 `structural_min_score` 门控，低结构分时退化为纯内容检索。
- **title 精确命中误判**：需做标点归一（去《》、空格、全半角），边界 cheap。
- **重索引成本**：obsidian 笔记量大时重建耗时可观，建议夜间/闲时执行，并在 `wipe=True` 前确认备份。

## 八、评测方式

沿用现有 RAGAS 评测（`config.py` 已配 `ragas_*`）。对比三组：

1. **baseline**：当前 dense+sparse（β=0，无前缀）。
2. **阶段一**：仅前缀（dense/BM25/reranker 感知结构）。
3. **阶段二**：前缀 + β 叠加（β 在 0.15 / 0.25 / 0.35 三档网格搜索）。

重点看 **recall@k** 与 **ndcg@k**（层级类 query 应显著提升），同时盯 **faithfulness / answer_correctness**
（确保不被结构加权带偏答案质量）。

## 十、与其他预留切分策略（v1/v2/v2b/v3）的关系与边界

用户曾疑问：本次「层级结构检索」是否就是 `splitter.py` 里预留但未实现的 `v2b`（父子层级）或 `v3`（chunk 级 wikilink）？
**结论：否。三者属于不同维度，本次既没实现也没替代 v2b/v3，仅在其一个子痛点上"蹭"了些价值。**

### 1. 三者维度对照

| 维度 | 策略 | 状态 | 管什么 |
|---|---|---|---|
| Chunking 切分策略层 | `v1` 单层 Recursive（基线） | 已实现 | 怎么切（粗） |
| | `v2` 两层 Header+Recursive（生产在用） | 已实现 | 怎么切（保留标题层级） |
| | `v2b` Parent-Child 双存 | `NotImplementedError`（Day3 评估） | 父子双存：子块检索精准、父块返回完整上下文 |
| Metadata 粒度层 | 整篇级 wikilink（现状） | 已实现（per-document） | 标注多细 |
| | `v3` chunk 级 wikilink | `NotImplementedError`（Day3 预研） | 每 chunk 只带自己段落里的 wikilinks，图关联更精准 |
| Retrieval 检索/排序层 | 本次「结构检索」（机制 A+B） | 已实现 | 怎么排（层级优先） |

### 2. 与 v3（chunk 级 wikilink）：完全正交

- **v3 动的是 `wikilinks` 元数据粒度**，目标是笔记**间关联图**精准（知道哪个 chunk 链到哪篇笔记）。
- 本次结构检索用的是 `heading_path / title / filepath / dir` 这套元数据 + 文本前缀，目标是**层级定位与排序优先**。
- 二者是两套完全不同的元数据、两个目标；本次**连 wikilink 的粒度都没碰**——`ingestor.py` 仍写 `c.metadata["wikilinks"] = node.wikilinks`（整篇级）。`split_v2` 注释也明写 "wikilinks 整篇级缝入每个 chunk（Day3 可升级到 chunk 级）"，这正是 v3 的活，至今仍是整篇级。

### 3. 与 v2b（父子双存）：部分缓解，但未替代

- **v2b 本质**：`parent_chunks`（HeaderSplitter 未细切的大段，保留完整上下文）+ `children`（细切小块，检索精准）+ `child_to_parent` 映射。检索用子块、返回 LLM 用父块，解"切太细丢上下文 vs 切太粗不精准"的两难。
- **本次机制 A（heading_path 前缀）与其关系**：把 `标题路径` 拼进**每一个** chunk，于是每个 chunk 都自带"我在哪个章节下"——这**部分缓解**了 v2b 想解决的一个子问题（chunk 不知道自己的层级位置）。
- **但 v2b 的真正价值本次没做**：父子双存 + "小检索 / 大返回"。当前每个 chunk 仍是独立一整块（前缀+正文），没有"子块命中后回退父块"的机制。v2b 在 Day3 仍值得单独评估，尤其当单篇笔记很长、一个 h2 下内容远超 chunk_size 时。

### 5. 一句话总结

v1/v2/v2b 管「怎么切」，整篇级/v3 管「标注多细」，本次结构检索管「怎么排」。本次只在「怎么排」这层动刀；**v2b 已于 2026-07-29 实现**（详见独立设计稿 [父子双存切分（v2b）设计方案.md](./父子双存切分（v2b）设计方案.md)，含双存储落库与父块展开），机制 A 顺手缓解的"chunk 缺层级上下文"痛点已通过 v2b 父块返回真正解决；**v3（chunk 级 wikilink）仍处 stub**——仍缺消费方，暂无实现必要。

## 十一、向量库落库结构（物理层）

理解本机制与 v2b/v3 的差异，关键是看清它们在 ChromaDB 里**到底怎么存**。

### 1. 当前（v2 + 结构检索）的落库形态

`ingestor.upsert()` 每条记录 = `{id, documents(前缀+正文), embeddings(1024 维 bge-m3), metadatas}`。

- **机制 A** 拼进 `documents` → 因此同时进 **embedding（向量）** 与 **BM25**（BM25 由 `collection.get(documents)` 全量拉建）。
- **机制 B** 是**排序层**，`structural_score` 只写在返回的 `RetrievalResult` 上用于观察/调试，**不进库**（不进 embedding、不进 BM25）。
- `metadatas` 含：`title` / `heading_path` / `dir` / `filepath` / `wikilinks`(整篇级) / `tags`(已统一 str)。

### 2. v2b 父子双存：拆成「两个存储」

- **检索集合（collection）**：只放 child（C1/C2/C3），每条带 `documents` + `embeddings` + `metadata`，并被 `collection.get()` 全量拉建 **BM25**。检索只在 child 上跑。
- **文档存储（docstore）**：只放 parent（如整章 2000 字），**纯文本、不进 embedding、不进 BM25**，靠 child 的 `parent_id` 字段反向取用。
- **关键省算力点**：parent 若也进 embedding+BM25，既稀释检索又白烧算力；故"只存不检索"，命中 child 才按需取父块整章返回。同 LangChain `ParentDocumentRetriever` 模式。

### 3. v3 chunk 级 wikilink：只改字段 + 一份图

- **集合不变**：每条 chunk 仍是 `documents + embeddings + metadatas`；只把 `metadata.wikilinks` 的值，从"全篇链接列表"收成"该 chunk 正文实际出现的链接"。
- 因 `wikilinks` 是 **metadata 非 documents**，它本就不进 embedding/BM25（当前检索完全不看它）；v3 只让这个一直空闲的字段变精准。
- **真正新增**：一份 `wikilink_graph`（邻接表：笔记标题 → 邻居列表），可存内存 dict / pickle / 单独 collection。但这份图**当前无任何检索逻辑消费**——v3 做完若不补"消费方"（图谱问答、相关文档推荐、rerank boost），chunk 级粒度即白做。

### 4. 三者物理差异对照

| | 当前(v2+结构检索) | v2b 父子双存 | v3 chunk 级 wikilink |
|---|---|---|---|
| 集合数量 | 1 | 2（检索集合 + docstore） | 1 |
| 是否新增 embedding | 否（仅文本变） | 否（parent 不 embedding） | 否 |
| 是否影响现有检索 | 是（前缀进向量） | 是（检索只在 child，返回换 parent） | 否（wikilinks 不参与检索） |
| 落地前提 | 已生效 | 需实现 + 双存储 | 需实现 + 配"消费方" |

## 十二、切分策略切换机制（启动前切换）

用户澄清：所谓"灵活切换"指**启动前切换**（改 config + 重建向量库），而非运行时热插拔。

### 1. 思路正确，但"开关"本身还没建

"启动前切换 = 改 config + `index_vault(wipe=True)` 重建"是标准做法，且**重建链路已验证跑通**（第九节 11,744 chunks）。但当前**没有选择开关**——

- `config.py` 只有 `chunk_size=800` / `chunk_overlap=150`，**无 `chunking_strategy` 字段**。
- `ingestor.py:141` **写死调用 `split_v2`**（import 也只引它，line 10）。

故"改 config 即切"现在做不到。

### 2. 现状实证

| 事实 | 位置 |
|---|---|
| config 无 `chunking_strategy` | `config.py:53-54` |
| ingestor 写死 `split_v2` | `ingestor.py:10, 141` |
| `split_v1` / `split_v2` 均已完整实现（有 return） | `splitter.py:79, 108` |
| `split_v2b` / `split_v3` 是 `NotImplementedError` 空壳 | `splitter.py:156→168, 174→184` |

### 3. 三种切法的支持度

| 切到 | 现状 | 能否启动前切换 |
|---|---|---|
| v2 ↔ v1 | 两路代码现成，只差选择开关 | ✅ 差 ~12 行（config 枚举 + ingestor 按配置选 splitter + make_splitters 参数化） |
| ↔ v2b | 空壳未实现 | ❌ 连切都切不过去（raise） |
| ↔ v3 | 空壳未实现 | ❌ 同上 |

### 4. ⚠️ 关键坑：切到 v1 会伤结构检索

`split_v1` 是扁平 Recursive 切分，**不解析标题层级 → 无 `heading_path`**。而我已落地的结构检索：

- **机制 A 前缀**：切 v1 后前缀只剩「目录 › 《文档名》」，无"分级标题"段。
- **机制 B 结构分**：`heading_path` 权重占 0.3，v1 下恒为 0。

→ 切到 v1，结构检索退化成"只剩文档名+目录"级别。这恰是 v2 比 v1 强之处。即便建了开关，v1 在"层级检索"维度仍弱于 v2。

### 5. 结构检索横切所有切分

机制 A（ingestor 拼前缀）+ 机制 B（hybrid 加结构分）作用于 ingestor/hybrid，**与选哪个 splitter 无关**：切 v2 时完整生效，切 v1 时自动退化。先上结构检索、再纠结切分选型，正是因此解耦。

### 6. 启动前切换开关（已实现，2026-07-29）

最小实现（约 12 行，零回归）：

1. `config.py` 加 `chunking_strategy: Literal["v1","v2"] = "v2"`（默认 v2，含 `from typing import Literal`）。
2. `ingestor.py` 按 `settings.chunking_strategy` 选 `split_v1`/`split_v2`；`make_splitters()` 仍返回 `(hs, cs)`，v1 只用 `cs`（child_splitter）。
3. 重建向量库即生效；v2b/v3 等实现后再加枚举值。

#### 实现要点
- `ingestor.py:141` 由写死 `split_v2` 改为分支：v1 走 `split_v1(node, cs)`（扁平、无 `heading_path`），v2 走 `split_v2(node, hs, cs)`。
- 机制 A/B **横切其上**：v2 时结构检索完整生效（`heading_path` 存在）；v1 时自动退化（前缀只剩「目录 › 《文档名》」，`structural_score` 的 heading 权重 0.3 恒为 0）。正是本节第 4 点约定的"切 v1 伤结构检索"。
- **使用方式**：在 `.env`（或环境变量）设 `CHUNKING_STRATEGY=v1`（或 v2），再执行第六节重索引命令即可切换；运行时不热插拔。
