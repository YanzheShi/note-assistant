# 图片多模态理解与检索设计方案

> 状态：设计稿（未动代码）
> 关联：`docs/父子双存切分（v2b）设计方案.md`、`docs/层级检索与结构优先设计方案.md`
> 目标：让 Obsidian 笔记里的图片从「被丢弃的路径字符串」变成**可理解、可检索、可引用、可显示**的一等公民资产。

---

## 零、TL;DR

**现状结论：图片链路是断的，而且断在 6 个独立的地方，任何一处修好都不够。**

- 图片的**视觉内容 100% 丢失**——系统只见过路径字符串和 alt 文本，从未"看过"图。
- 更糟的是：本该保护图片的 `RichPreprocessor` **整条链路空转**——`ingestor.py` 算出了 `cleaned` 文本却从未使用，切分器直接吃 `node.raw_md`。所以 `restore()` 找不到任何占位符，`has_image` 等 metadata **永远不会被写入**。
- 前后端契约冲突：`SourceInfo.type` 的值域是 `direct|graph`，`SourceSchema.type` 的值域是 `text|table|mermaid|image`，API 层直接透传 → 前端 `src_type == "image"` **永远为假**，图片渲染分支是死代码（而且它还被错误缩进包在了另一个分支里）。

**方案主线**：引入 **ImageAsset 资产层**（内容哈希主键 + 引用点解耦）→ **结构化图表原生解析层**（5.B：Excalidraw/draw.io/PlantUML/Mermaid/SVG 零 VLM 解析为 DiagramGraph，可检索可原生渲染）→ **VLM 结构化理解层**（仅兜底截图/照片，产出 8 字段 JSON 且 mermaid 须校验）→ **双通道索引**（正文内联摘要 + 独立 image chunk）→ **检索/生成/展示闭环**（图片 URL 服务 + `render_hint` 原生渲染 + 答案内嵌图）。

分四期落地，P0 是纯 bug 修复（零成本、必须先做），**P1 第一步先做零成本的图表原生解析层**，再引入多模态 LLM。

### 1.1 当前图片"处理"的真实路径

```

        ↓

        ↓  → 产出 cleaned（★ 这个返回值被丢弃了 ★）

        ↓
generate_summaries()              ← 唯一真正生效的部分，产出 "图片: xxx.png (alt | 上下文)"
        ↓

```

### 1.3 真实 vault 的图片形态（实测 `D:\Note\test`，288 篇笔记）

```
总图片引用 25 处，分布在 6 篇笔记
形态分布：
  - 远程 URL  ![描述](https://oss.javaguide.cn/.../agent-memory-arch.png)   ← 主力
  - 远程 SVG  ![...](https://.../agent-memory-taxonomy.svg)                 ← 占比不低
  - Obsidian 嵌入 ![[Pasted image 20260724160557.png]]                      ← 附件文件不在 vault 内
  - 本地相对 ![](/logo.png)
vault 内实际图片文件：0 个
```

**这个分布直接影响设计取舍**：

- 远程 URL 是主力 → **必须有下载 + 本地缓存 + 失败降级**，不能假设图片在本地。
- SVG 占比不低 → SVG 里的 `<text>` 节点是**免费的高质量文本信号**，比 VLM 更准更便宜，必须优先抽取；栅格化只作为补充。
- 远程图的 alt 通常写得不错（`![AI Agent 记忆系统架构](...)`）→ alt 是**有价值的先验**，应作为 VLM 的输入提示而非被覆盖。
- `Pasted image xxx.png` 这种零信息命名 → **只有 VLM 能救**，是本方案的核心价值场景。

## 二、设计目标与非目标

### 2.1 目标

| 编号 | 目标 | 验收标准 |
|---|---|---|
| G1 | 图片内容不丢失 | 每张非装饰性图片都有结构化语义记录，落盘可审计 |
| G2 | 可检索 | 问「那张记忆系统架构图讲了什么」能召回对应 image chunk，Recall@5 ≥ 0.8 |
| G3 | 可引用 | LLM 回答中能引用图片并说明图中内容，不编造 |
| G4 | 可显示 | 前端来源区能渲染缩略图，答案正文里的图能直接显示 |
| G5 | 成本可控 | 全量索引的 VLM 调用可预算、可缓存、可跳过；增量索引图片零重复调用 |
| G6 | 零回归 | 总开关关闭时，行为与改造前逐字节等价 |

### 2.2 非目标（本期不做）

- 不做以图搜图（CLIP 双塔）——列入 Phase 3 可选。
- 不做视频/音频附件。
- 不做图片编辑、生成。
- 不改 Obsidian 原始笔记文件（**硬约束**：与项目既有的「never modifies user notes」原则一致）。

## 三、总体架构

```
┌─ 资产层 Asset Layer ──────────────────────────────────────────┐
│  ImageRef（引用点：哪篇笔记、哪个章节、alt、原始语法）           │
│  ImageAsset（物理资产：content_hash 主键、mime、尺寸、本地缓存） │
│  AttachmentIndex（Obsidian 短名 → 真实路径，最短唯一路径规则）   │
│  RemoteFetcher（URL 下载 + ETag + 本地缓存 + 失败降级）          │
└──────────────────────────┬───────────────────────────────────┘
                           ↓
┌─ 理解层 Vision Layer ─────────────────────────────────────────┐
│  ① 廉价预判：装饰图/正文图分类（尺寸、比例、体积、SVG 文本密度） │
│  ② SVG 文本直取（免费高质量信号，无需 VLM）                     │
│  ③ VLM 结构化理解（8 字段 JSON schema + 上下文增强 prompt）     │
│  ④ VisionCache（sha256 + prompt_version + model_id 三元 key）  │
│  ⑤ 并发限流 / 退避重试 / 超时 / 全局预算护栏 / 降级             │
└──────────────────────────┬───────────────────────────────────┘
                           ↓
┌─ 索引层 Index Layer ──────────────────────────────────────────┐
│  通道 A：正文 chunk 内联 —— 原始 markdown + 一句话摘要注释      │
│  通道 B：独立 image chunk —— 完整描述 + OCR + 实体，进向量库     │
│  BM25：OCR 文本单独进稀疏索引（专有名词/数字，dense 召不回）     │
│  v2b 兼容：image chunk 挂 parent_id → 命中可回退整节            │
└──────────────────────────┬───────────────────────────────────┘
                           ↓
┌─ 检索层 Retrieval Layer ──────────────────────────────────────┐
│  同池竞争 + reranker（输入本就是文本，天然兼容）                │
│  图意图识别 → image chunk 权重微调                              │
│  命中 image chunk → 自动带出所在章节文本邻居（图不能脱离上下文） │
└──────────────────────────┬───────────────────────────────────┘
                           ↓
┌─ 生成层 Generation Layer ─────────────────────────────────────┐
│  context 里 image chunk 结构化渲染 + [[IMG:asset_id]] 引用标记  │
│  答案后处理：引用标记 → 可访问 URL → markdown 图片语法          │
│  （可选）on-demand vision：原图 base64 直投最终 LLM             │
└──────────────────────────┬───────────────────────────────────┘
                           ↓
┌─ 服务/展示层 ────────────────────────────────────────────────┐
│  GET /assets/{asset_id}  静态图片服务（ETag / Cache-Control）   │
│  SourceSchema 契约修正：origin 与 kind 分离                     │
│  前端：来源区缩略图 + 答案正文内嵌图                             │
└──────────────────────────────────────────────────────────────┘
```

## 四、资产层设计

### 4.1 数据结构（新增 `indexing/assets.py`）

```python
@dataclass
class ImageRef:
    """图片引用点 —— 一次 markdown 里的出现。"""
    raw_syntax: str        # 原始语法 "![架构图](https://...)" 或 "![[Pasted image.png]]"
    src: str               # 语法里写的地址（URL / 短名 / 相对路径）
    alt: str               # alt 文本（可能为空）
    note_filepath: str     # 所在笔记（相对 vault 根）
    heading_path: str      # 所在章节，如 "三、记忆架构 > 3.2 分层"
    char_offset: int       # 在 raw_md 中的偏移（定位/排序用）
    context_before: str    # 前 300 字正文（已剥离其他占位符）
    context_after: str     # 后 300 字正文
    asset_id: str = ""     # 解析成功后回填

@dataclass
class ImageAsset:
    """物理图片资产 —— 以内容哈希为主键，跨笔记天然去重。"""
    asset_id: str          # sha256(bytes)[:16]，主键
    source_kind: str       # "local" | "remote" | "missing"
    origin: str            # 原始 URL 或 vault 内绝对路径
    local_path: str        # 本地缓存路径 data/assets/<asset_id>.<ext>
    mime: str              # image/png | image/svg+xml | ...
    width: int
    height: int
    bytes_size: int
    etag: str = ""         # 远程图的 HTTP ETag（增量判断用）
```

**关键设计：ImageRef 与 ImageAsset 一对多解耦。**
同一张架构图被 3 篇笔记引用 → 3 个 ImageRef、1 个 ImageAsset → **VLM 只调用 1 次**。这是成本控制的第一道闸门，也是为什么主键必须是内容哈希而不是路径。

### 4.2 Obsidian 短名解析（AttachmentIndex）

Obsidian 的 `![[Pasted image 20260724160557.png]]` 不带路径，靠**最短唯一路径**规则解析。必须复刻：

1. 启动时 `rglob` 全 vault 的图片扩展名（`.png/.jpg/.jpeg/.gif/.webp/.bmp/.svg/.excalidraw/.drawio/.xml/.plantuml/.puml/.mmd/.mermaid`），排除隐藏目录（复用 `VaultLoader.scan` 的排除逻辑）。其中 `.drawio/.xml/.plantuml/.puml/.mmd/.mermaid` 是**结构化图表源文件**，交由 5.B 节的原生解析层处理，不再当普通图片。
2. 建两级索引：`filename → [paths]`（可能重名）和 `relpath → path`（精确匹配优先）。
3. 解析顺序：**精确相对路径 → 引用笔记同目录 → 配置的 attachment 目录 → 全库唯一文件名 → 重名时按目录树距离最近**。
4. 全部落空 → `source_kind="missing"`，记录告警但**不中断索引**（笔记里图挂了是常态，不能因此索引失败）。

### 4.3 远程图片获取（RemoteFetcher）

- 下载到 `data/assets/<asset_id>.<ext>`，先下到临时文件再原子 rename（防半截文件）。
- 记录 `ETag` / `Last-Modified`，增量索引时先发 `HEAD`，命中则跳过下载与 VLM。
- 超时 10s、重试 2 次（指数退避）、并发上限，失败标记 `missing` 并降级到「alt + 上下文」。
- 大小护栏：> `image_max_bytes`（默认 10MB）跳过；尺寸 > 4096px 先本地缩放到长边 1536 再送 VLM（省 token，VLM 对超大图也没额外收益）。
- **隐私开关**：`image_allow_remote_fetch`，关闭则只处理本地资产（企业/敏感场景）。

## 五、理解层设计（多模态 LLM 的落点）

### 5.1 分级路由：不是所有图都值得调 VLM

```
图片 → [廉价预判] ─→ decorative（分割线/logo/emoji/极小图/极端宽高比）→ 跳过，只留 alt
                  ├→ SVG → 先抽 <text> 文本；文本密度足够 → 直接用，不调 VLM
                  └→ 其余 → 进 VLM 队列
```

预判规则（纯本地、零成本）：

| 规则 | 阈值 | 判定 |
|---|---|---|
| 面积 | < 100×100 px | decorative |
| 宽高比 | > 10:1 或 < 1:10 | decorative（分割线/横幅） |
| 文件体积 | < 5KB | decorative |
| 文件名 | 匹配 `logo\|icon\|badge\|divider\|avatar` | decorative |
| SVG 内 `<text>` 字符数 | ≥ 30 | 文本直取，跳过 VLM |

实测 vault 里的 `![](/logo.png)`、`interview-guide-banner.png` 会被这层拦掉，直接省掉无效调用。

### 5.2 结构化输出 schema（工业级与玩具的分水岭）

**不要只让 VLM 输出一句 caption。** 一句 caption 既检索不好（信息密度低）又生成不好（LLM 无细节可用）。强制 JSON schema：

```jsonc
{
  "image_type": "architecture_diagram|flowchart|chart|screenshot|table_image|formula|photo|decorative",
  "title": "简短标题，≤20字",
  "summary_short": "一句话摘要，≤50字。用于内联进正文 chunk",
  "description": "150-400字结构化描述：画了什么、有哪些组件、组件间关系与流向、想表达的结论",
  "ocr_text": "图中所有可见文字，逐字抄录，保持原有换行与层级",
  "entities": ["MoE", "Attention", "KV Cache"],
  "data_points": "图表类专用：坐标轴含义、系列名、关键数值与趋势；非图表填空串",
  "mermaid_equivalent": "仅由 VLM 在「截图/照片流程图」兜底时产出（见 5.B.8）；结构化图表源文件（Excalidraw/draw.io/PlantUML/Mermaid/SVG）由原生解析层生成 `render_hint`，优先于本字段。非流程图或兜底失败填空串",
  "confidence": 0.0
}
```

三个字段的用途各不相同，缺一不可：

- `summary_short` → 内联进正文 chunk，保证正文不断裂。
- `description` + `entities` → 进 dense 向量，负责语义召回。
- `ocr_text` → 进 BM25 稀疏索引。**图里的专有名词、版本号、代码片段、数字，dense 向量几乎召不回，BM25 是唯一解。**
- `mermaid_equivalent` → 仅限截图/照片流程图兜底（见 5.B.8），且须语法校验。**结构化图表优先用 `render_hint`（原生 mermaid/drawio/svg 渲染，零幻觉）**，该字段是降级通道而非首选。

### 5.3 上下文增强的 Prompt（关键工业细节）

**裸图 caption 会跑偏。** 同一张「三层方框图」，在《Agent 记忆》笔记里是记忆分层，在《网络协议》笔记里是协议栈。必须把上下文喂进去：

```
[System]
你是技术笔记图片理解专家。严格按给定 JSON schema 输出，不要输出任何解释文字。
规则：
1. ocr_text 必须逐字抄录图中文字，不得改写、翻译、省略
2. description 只描述图中确实存在的内容，禁止根据上下文推测图中没有的东西
3. 若图片模糊/无实质内容，image_type 填 decorative，confidence 填 0.2 以下
4. 上下文仅用于消歧术语和确定领域，不得当作图的内容写进 description

[User]
<image>
—— 以下是该图片在笔记中的位置信息（仅供消歧）——
笔记标题：{note_title}
所在章节：{heading_path}
图片 alt：{alt}
图片前文：{context_before}
图片后文：{context_after}
```

第 4 条规则是**防幻觉的核心**：上下文既要给（消歧），又要明确禁止污染描述（否则 VLM 会把正文内容复述成"图中内容"，制造检索假阳性）。

### 5.4 缓存与幂等

`data/vision_cache.sqlite`：

```sql
CREATE TABLE vision_cache (
  cache_key    TEXT PRIMARY KEY,  -- sha256(asset_id|prompt_version|model_id|context_hash)
  asset_id     TEXT NOT NULL,
  result_json  TEXT NOT NULL,
  model_id     TEXT NOT NULL,
  prompt_ver   TEXT NOT NULL,
  tokens_used  INTEGER,
  created_at   TEXT NOT NULL
);
CREATE INDEX idx_asset ON vision_cache(asset_id);
```

- `context_hash` 参与 key：同一张图在不同笔记里的理解结果不同，各存一份。
- `prompt_version` 参与 key：改 prompt 必须 bump 版本才重跑，避免"改了 prompt 但缓存还是旧的"这类隐性 bug。
- 换模型（`model_id` 变）自动失效重跑。
- 重索引同一 vault → 缓存命中率应 ≈ 100%，成本为零。

### 5.5 并发、降级与成本护栏

| 机制 | 设计 |
|---|---|
| 并发 | `asyncio.Semaphore(image_vlm_concurrency)`，默认 4 |
| 超时 | 单张 60s |
| 重试 | 2 次指数退避（1s / 4s），仅对 5xx / 超时 / 网络错误重试 |
| JSON 校验 | 输出用 pydantic 校验；失败重试 1 次并在 prompt 追加"上次输出不是合法 JSON"；再失败降级 |
| 降级 | 任何失败 → 退回 `alt + 上下文` 的旧行为，`confidence=0`，索引继续，**绝不因图片失败中断整库索引** |
| 预算护栏 | 单次索引 VLM 调用上限 `image_vlm_max_calls_per_run`（默认 500），超限则剩余图片标记 `pending`，由 `scripts/backfill_images.py` 异步补齐 |
| 可观测 | 索引结束打印：图片总数 / 跳过数 / 缓存命中 / VLM 调用 / 失败数 / 累计 token |

**「先建索引、后补图片理解」是硬要求**——不能让首次索引因为 500 张图卡住 40 分钟。

> **规模适配说明（针对"25 张图用不上这些护栏"的质疑）**：本 vault 仅 25 张图，并发/预算护栏/异步 backfill 在本库近乎 no-op，承认这一点。但它们属于**通用护栏**，对大库（数百~数千图）才是必要的，成本极低、可一键关闭，保留无碍。真正对 25 张图**不可省**的是**远程 URL 获取层**（下载+缓存+ETag）——因为本 vault 图片以远程 `oss.javaguide.cn` 为主，不抓取就根本无法渲染。装饰图预判与 SVG 文本抽取则同时提升质量（降噪）而非只为省钱，任何规模都该做。

## 五-B、结构化图表原生解析层（流程图 / 架构图优先于 VLM）

> 本轮补丁的起因：原设计把「流程图」只当成「栅格图片的一个子类型」，让 VLM 顺手产出 `mermaid_equivalent`。这是**最结构化的图用了最弱的处理**——Excalidraw / draw.io / PlantUML / Mermaid / SVG 流程图本可以零成本、零幻觉地解析，却被一律丢进 VLM 队列，既浪费 token，又因 VLM 硬转 mermaid 语法不可靠而前端渲染崩。本节把它们单独立法。

### 5.B.1 为什么流程图不能当栅格图处理

| 来源 | 本质 | 信息是否可读 | 正确做法 |
|---|---|---|---|
| 截图 / 照片里的流程图 | 栅格像素 | 不可读，必须 VLM | VLM 兜底（见 5.B.8） |
| **Excalidraw**（`.excalidraw`） | JSON：图形 + 文本 + 箭头 | **完全可读** | 原生解析，**不调 VLM** |
| **draw.io / diagrams.net**（`.drawio`/`.xml`） | XML：mxGraph 节点与边 | **完全可读** | 原生解析，**不调 VLM** |
| **PlantUML**（`.plantuml`/`.puml`） | 文本 DSL | **完全可读** | 原生解析，**不调 VLM** |
| **Mermaid 文件**（`.mmd`/`.mermaid`）或笔记内 ```` ```mermaid ```` | 文本 DSL | **完全可读** | 原生解析，**不调 VLM** |
| **SVG 流程图** | XML：`<rect>`/`<path>`/`<text>` + 箭头 | 部分可读 | 抽 `<text>` **且**解析图形结构（见 5.B.4.5） |

核心判断：**凡是「源文件本身就是结构化图」的，绝不送 VLM。** VLM 只用于像素级的截图/照片流程图，且产出必须经过语法校验（5.B.8）。

> **本 vault 实测对 5.B 的约束（决定优先级）**：`D:\Note\test` 中 `.excalidraw/.drawio/.plantuml/.puml/.mmd/.mermaid` **文件数 = 0**；但 ```` ```mermaid ```` **代码块出现在 29 篇笔记**中，且远程 SVG（`oss.javaguide.cn`）占比不低。结论：**Mermaid 代码块路径（5.B.4.4）+ SVG 路径（5.B.4.5）在本 vault 有真实命中，列入 P1/P2；Excalidraw / draw.io / PlantUML 文件解析器（5.B.4.1~5.B.4.3）本 vault 零命中，降为 P3 可选**——它们是面向通用 Obsidian 的防御性建设（Excalidraw 是 Obsidian 里最普遍的绘图格式），非本 vault 必需，不要为了 0 个文件优先做。

### 5.B.2 来源识别与路由优先级

路由发生在「理解层 VLM 之前」，由 `DiagramRouter` 在资产层（`assets.py`）解析出 `mime` 后即刻判定：

```
ImageAsset
  ├─ mime == image/svg+xml        → SVGParser（抽 text + 图形结构）
  ├─ ext == .excalidraw          → ExcalidrawParser
  ├─ ext ∈ {.drawio,.xml}        → DrawIOParser
  ├─ ext ∈ {.plantuml,.puml}     → PlantUMLParser
  ├─ ext ∈ {.mmd,.mermaid}       → MermaidParser
  ├─ 笔记内 ```mermaid 代码块     → MermaidParser（复用 preprocessor 提取结果）
  └─ 其余栅格（png/jpg/...）      → 进 VLM 队列（5.1 分级路由）
```

> 注意：`assets.py` 的扩展名扫描（4.2 节）必须补充 `.drawio/.xml/.plantuml/.puml/.mmd/.mermaid`，否则这些文件当前会被 `AttachmentIndex` 直接漏掉。

### 5.B.3 统一中间表示：DiagramGraph

所有原生解析器输出同一个模型，后续检索与渲染只认这一个结构：

```python
@dataclass
class DiagramGraph:
    diagram_type: str          # flowchart|sequence|class|architecture|mindmap|unknown
    title: str                 # 取文件名 / 首行 title / 父笔记标题
    nodes: list[DiagramNode]   # 节点
    edges: list[DiagramEdge]   # 边（流程/关系）
    raw_text: str              # 原始 DSL / 拼接后的可读文本（用于 BM25）
    render_hint: str           # "mermaid:<source>" | "drawio:<path>" | "svg:<path>"，前端据此原生渲染
    source_format: str         # excalidraw|drawio|plantuml|mermaid|svg

@dataclass
class DiagramNode:
    id: str
    label: str                 # 节点文字（已清洗）
    shape: str                 # rect|ellipse|diamond|cylinder|...
    group: str = ""            # 子图/分组（如有）

@dataclass
class DiagramEdge:
    from_id: str
    to_id: str
    label: str = ""            # 边上的条件/说明文字
```

`raw_text` 是把「节点标签 + 边标签 + 分组」拼成的纯文本，**直接喂 BM25 + dense**，质量远高于 VLM caption（节点名、判断分支、专有名词一个不丢）。

### 5.B.4 各格式解析器规格

**5.B.4.1 Excalidraw（`.excalidraw`）**
- JSON 文件。`elements[]` 中 `type` ∈ {rectangle, ellipse, diamond, arrow, text, frame…}。
- 文本来自 `type=="text"` 的 `text` 字段；图形上的文字来自 `type=="text"` 且被 arrow/container 关联的绑定。
- 边来自 `type=="arrow"` 的 `startBinding.endpointId` / `endBinding.endpointId`。
- 还原顺序：先建节点表 → 再连 arrow 绑定 → 按 `x,y` 估算布局（仅用于 `render_hint`，不用于检索）。
- 形状推断：`rectangle`→rect，`ellipse`→ellipse，`diamond`→diamond。
- 坑：Excalidraw 文本可能按字符拆成多个 element（bound text），需按 `containerId` 聚合。

**5.B.4.2 draw.io / diagrams.net（`.drawio`/`.xml`）**
- XML，根 `<mxGraphModel>`，节点 `<mxCell vertex="1">`，边 `<mxCell edge="1" source=.. target=..>`。
- 节点文字在 `value` 属性（可能含 HTML，需去标签）；形状在 `style`（如 `rounded=1;shape=rhombus`）。
- 边文字在 `value`；方向由 `source`/`target` id 直接给出，无需推断。
- 支持子图（`<mxCell>` 嵌套 `parent`）。

**5.B.4.3 PlantUML（`.plantuml`/`.puml`）**
- 文本 DSL，直接当 `raw_text` 建索引。
- 若需前端可视化：走 `plantuml` 服务端或 `@plantuml` 本地 jar 渲染为 SVG（新增可选依赖）；否则 `render_hint="text:plantuml"`，前端以等宽代码块展示。
- 解析节点/边用于 `DiagramGraph`：用轻量正则提取 `@startuml` 块、`actor`/`participant`/`class`/`:A->B:` 等语句——**仅用于生成可读文本与边关系，不追求 100% 覆盖所有语法**。

**5.B.4.4 Mermaid（`.mmd`/`.mermaid` 文件，及笔记内 ```` ```mermaid ```` 代码块）**
- 文件：整段作为 `raw_text` 建索引；`render_hint="mermaid:<source>"` 前端直接 `mermaid.render`。
- 笔记内代码块：复用 `preprocessor.py:_extract_mermaid` 已提取的 `ExtractedChunk(kind="mermaid")`，**P0 修好 `raw_mermaid` 不为 None 后**，把该 chunk 当 `DiagramGraph(raw_text=chunk.raw, render_hint="mermaid:inline")` 处理，进入检索与可渲染来源。
- 解析节点/边：用 `mermaid` 官方 parser（`mermaid.parse` / `@mermaid-js/parser`）抽取，得到 `DiagramGraph`，用于结构化检索文本（比裸源码检索更稳）。

**5.B.4.5 SVG 流程图（`image/svg+xml`）**
- **不止抽 `<text>`**（修正 5.1 的「文本达标跳过 VLM」逻辑）：还要解析图形结构。
- 节点：`<rect>/<ellipse>/<polygon>/<path>` 带文字绑定者 → `DiagramNode`。
- 边：`<path>`/`<line>`/`<polyline>` 带 `marker-end`（箭头）或 `stroke` 连线 → 按坐标邻近匹配端点 → `DiagramEdge`。
- `raw_text` = 所有 `<text>` 拼接 + 边标签。
- 若结构解析置信度低（纯装饰 SVG / 图标），降级回 5.1 的「文本直取，跳过 VLM」。
- `render_hint="svg:<path>"`：前端直接 `<img src=...>` 或内联 SVG 渲染，无需转译。

### 5.B.5 检索策略（结构化文本优于 caption）

原生解析产出的 `DiagramGraph.raw_text` 与 `description`（无，因为没调 VLM）按两条通道入索引（复用第六章双通道）：

- **通道 A（正文内联）**：在笔记 chunk 内联一行「【流程图·<title>】<nodes 摘要>」，保证正文不断裂且能被搜到。
- **通道 B（独立图 chunk）**：`content = raw_text`，`image_type` 置 `flowchart`/`architecture` 等，`render_hint` 写入 metadata。
- `raw_text` 同时进 dense（语义）与 BM25（节点名/分支/专有名词密集，BM25 命中率极高）。
- 图意图识别（7.2）命中时，这类 chunk 同样享受 `image_intent_boost`。

> 对比 VLM 路径：原生层零 token、零幻觉、节点/边 100% 保真；VLM 路径的 `mermaid_equivalent` 仅作截图流程图的兜底（见 5.B.8）。

### 5.B.6 渲染闭环（零幻觉）

`SourceSchema`（9.2 修正后）新增 `render_hint` 字段，前端按值分发：

| render_hint | 前端行为 |
|---|---|
| `mermaid:<source>` | `mermaid.render(source)` 渲染可交互流程图 |
| `drawio:<path>` | 内联 draw.io 查看器 / `<img>` |
| `svg:<path>` | 内联 SVG / `<img>` |
| `text:plantuml` | 等宽代码块展示源码 |
| `image:<path>` | 普通图片（VLM 兜底路径） |

前端不再依赖「VLM 猜的 mermaid 字符串」，而是渲染**源文件本身的结构**，彻底消除「mermaid_equivalent 语法错误导致渲染崩」。

### 5.B.7 与 5.2 schema 的关系

原 `mermaid_equivalent` 字段语义收窄为：**仅由 VLM 在「截图/照片流程图」兜底时产出**，且必须经过 5.B.8 校验才写入。结构化来源的 `render_hint` 优先于 `mermaid_equivalent`——前端先看 `render_hint`，为空才回退到 `mermaid_equivalent`。

### 5.B.8 截图 / 照片流程图的 VLM 兜底 + 校验

对确实只有像素的流程图，VLM 仍需产出 `mermaid_equivalent`，但加两道护栏：

1. **语法校验**：用 `mermaid.parse()` 验证；不合法 → 重试一次（prompt 注入「必须输出合法 mermaid，禁止注释与 HTML」）→ 仍失败则降级为 `description` 文本 + `render_hint="image:<path>"`，**绝不把非法字符串吐给前端**。
2. **复杂度上限**：节点数 > 30 或含跨子图跳转 → 放弃 mermaid，改用 `description` 文本检索（超复杂流程图转 mermaid 本身易错且前端渲染卡顿）。

### 5.B.9 成本与测试

- 成本：原生解析层对 Excalidraw/draw.io/PlantUML/Mermaid/SVG 是**零 VLM 调用**，直接把这部分流程图的边际成本降为 0；VLM 只处理真正的截图/照片。
- 测试：
  - 单测：5 种格式的 fixture（含一个嵌套子图的 draw.io、一个含 bound text 的 Excalidraw、一个跨子图的 PlantUML），断言 `DiagramGraph.nodes/edges` 还原正确、`raw_text` 不含 HTML 标签。
  - 渲染测试：mermaid/drawio/svg 的 `render_hint` 能被前端正确分发（mock 渲染器，断言不抛错）。
  - 回归：`mermaid_equivalent` 非法时降级路径不被吐给前端（断言 `render_hint=="image:..."` 或仅 `description`）。

## 六、索引层设计

### 6.1 前置：修复 preprocessor 空转（P0，不修则一切无从谈起）

改造 `ingestor.py` 与 `full_reindex.py`，让切分器吃 `cleaned` 而非 `node.raw_md`：

```python
cleaned, fm_chunks = preprocessor.process_with_meta(node)
node_for_split = replace(node, raw_md=cleaned)   # dataclasses.replace，不改原 node
chunks = split_v2b(node_for_split, hs, cs)
chunks = preprocessor.restore(chunks)            # 这次 restore 真的会生效
```

同时修 `_extract_images`：`ExtractedChunk.raw` 存**完整原始语法** `m.group(0)`，而不是 `img_path`。
新增 `ExtractedChunk.meta: dict` 字段承载 `asset_id / src / alt`，避免继续往 `context` 字符串里塞结构化信息（当前 `alt + " | " + context` 这种拼接是反模式）。

`context` 的取值改为**从原始 `md_text` 切窗口**，而不是从已被替换过占位符的 `text` 切——修掉 `<CODE_UID_xxx>` 污染上下文的问题。

### 6.2 通道 A：正文 chunk 内联

restore 时把图片占位符还原为：

```markdown
![AI Agent 记忆系统架构](https://oss.javaguide.cn/.../agent-memory-arch.png)
> 图 3：记忆系统三层架构——感知层写入、存储层分短期/长期、检索层按相关性召回
<!-- img:a3f2b1c88e5d4f10 -->
```

三行各有其职：

1. **原始 markdown 语法** → 前端 `st.markdown` 直接渲染，图能显示（远程 URL 天然可用；本地图重写为 `/assets/{asset_id}` 服务 URL）。
2. **引用式一句话摘要** → 让正文 chunk 在图片位置不出现语义断裂，同时被 dense/BM25 索引到。
3. **HTML 注释形式的 asset_id** → 机器可解析的回链锚点，且注释不会污染渲染效果。

> 注意 chunk_size 影响：每张图内联约增加 60-100 字符。当前 `chunk_size=800`，图密集的笔记 chunk 数会小幅上升，属可接受代价。

### 6.3 通道 B：独立 image chunk

`kind="image"`，`page_content` 组装：

```
{结构前缀}   ← 复用 build_structural_prefix，如 "18-IMA整理 › 《agent-memory》› 三、记忆架构"

[图片·架构图] AI Agent 记忆系统架构
图中内容：{description}
图中文字：{ocr_text}
关键概念：{entities 逗号连接}
{data_points}      # 图表类才有
```

metadata：

```python
{
  "kind": "image",
  "asset_id": "a3f2b1c88e5d4f10",
  "image_type": "architecture_diagram",
  "img_src": "https://oss.javaguide.cn/.../agent-memory-arch.png",
  "img_url": "/assets/a3f2b1c88e5d4f10",   # 服务端可访问 URL
  "filepath": "18-IMA整理/agent-memory.md",
  "title": "agent-memory",
  "heading_path": "三、记忆架构 > 3.2 分层设计",   # ← 修掉现状 summary chunk 缺 heading_path 的问题
  "parent_id": "...::parent::3",                  # ← v2b：命中图可回退整节
  "vision_confidence": 0.86,
  "has_ocr": True,
}
```

**这个 chunk 替换掉现有的 `generate_summaries()` 里的 image 分支**——现有那条 `图片: xxx.png (| ...)` 的噪声 chunk 直接废弃。

### 6.4 BM25 / 稀疏索引

`ocr_text` 必须进 BM25。理由：图里的 `bge-reranker-v2-m3`、`0.92`、`torch.nn.MultiheadAttention` 这类 token，bge-m3 dense 向量的召回率很差，而 BM25 精确匹配是免费的强信号。

实现上无需改 `sparse_retriever`——image chunk 的 `page_content` 已含 ocr_text，走现有构建流程即可。只需确认 BM25 分词器对图中英文/代码 token 的处理。

### 6.5 v2b 父子双存兼容

- image chunk 的 `parent_id` 挂到其所在章节的父块 → 命中图片时 `ParentDocstore` 回退整节，LLM 同时拿到图和上下文。
- 父块内容里保留通道 A 的内联形式（图 + 摘要），不塞完整 description（否则父块爆预算）。

## 七、检索层设计

### 7.1 同池竞争

image chunk 与文本 chunk 进同一个 ChromaDB collection，走同一套 hybrid + rerank。理由：

- reranker（`bge-reranker-v2-m3`）输入是纯文本 query-doc 对，image chunk 本就是文本，**天然兼容，零改造**。
- 单独建 image collection 会引入"融合两路结果"的新问题，得不偿失。

### 7.2 图意图识别（轻量、可选）

query 命中 `图|图片|截图|架构图|流程图|示意图|图表|画的|图中|diagram|chart|screenshot` → image chunk 融合分 `× (1 + image_intent_boost)`（默认 0.15）。

不做 LLM 意图分类——正则够用，且零延迟。boost 设小值避免"提到图就全是图"的翻车。

### 7.3 图文邻居扩展

命中 image chunk 时，自动把同 `heading_path` 的文本 chunk 补进上下文（若尚未命中，且未超 top_k）。

理由：**图片描述脱离上下文容易误导。** "图中画了三层架构"这句话，不配上正文的解释，LLM 很容易编造细节。这条与现有的 graph_expansion 机制并列，走同一套预算控制。

**双链路对称（已实现）**：该逻辑抽成共享纯函数 `expand_image_neighbors(results, fetch_fn, *, budget=6)`（位于 `pipeline/image_answer.py`），**`/ask`（rag_chain 委托）与 `/agent`（generate_node）两条链路共用**，保证对称。邻居按 `score=0` 置于 Top-K 截断之后补在末尾，**只进生成上下文、不回写累积结果**（不污染 sources / Judge 证据）。图片 chunk 判定用 `_is_image_chunk`：先认 `kind=="image"`（真实 VLM 图经 `classify_source` 透传会带上该标记），再兜底 `asset_id` + `image_description`/`image_ocr_text`——后者覆盖任何未写入 `kind` 的图片富化 chunk，比单纯 `kind=="image"` 更鲁棒（二者在现有数据上结果一致）。

## 八、生成层设计

### 8.1 context 渲染

`Generator._format_context` 增加类型分支：

```
### [3] 《agent-memory》› 三、记忆架构 【图片·架构图】
图中内容：记忆系统分为感知、存储、检索三层，感知层负责……
图中文字：Perception Layer / Short-term Memory / Long-term Memory / Retrieval
引用方式：如需引用此图，在回答中写 [[IMG:a3f2b1c88e5d4f10]]
```

### 8.2 System Prompt 增补

```
6. 参考笔记中标注【图片】的条目来自笔记里的插图，其内容由视觉模型解析得到。
   - 引用图片信息时，说明"根据笔记中的架构图"，不要说"根据文档描述"
   - 如果图片信息对回答有帮助，在相应位置插入 [[IMG:asset_id]] 标记，系统会自动替换为图片
   - 严禁描述图片解析结果中不存在的细节
```

### 8.3 答案后处理

流式输出结束后（或流式中做增量替换），把 `[[IMG:asset_id]]` 替换为 `![{title}]({img_url})`。

流式场景的实现要点：标记可能跨 token 边界，需维护一个小缓冲区，检测到 `[[IMG:` 开头就暂缓输出直到闭合或超长放弃。

### 8.4 （Phase 3 可选）on-demand vision

当满足以下任一条件，把**原图 base64 直接塞进最终生成 LLM 的 multimodal message**：

- 命中 image chunk 的 `vision_confidence < 0.5`
- query 明确指向图片细节（"图里第三个框写的什么"）
- 用户在前端点击"深入看这张图"

代价高（每张图 ~1-2k token），必须独立开关 `image_ondemand_vision_enabled`，默认关闭。这是"预计算 caption"路线的兜底，不是主路线。

### 10.1 sync.db 扩展

```sql
CREATE TABLE asset_state (
  asset_id     TEXT PRIMARY KEY,
  origin       TEXT NOT NULL,      -- URL 或本地绝对路径
  source_kind  TEXT NOT NULL,      -- local | remote | missing
  sha256       TEXT NOT NULL,
  etag         TEXT,
  vision_ver   TEXT,               -- 已完成理解的 prompt 版本
  status       TEXT NOT NULL,      -- ok | pending | failed | skipped
  updated_at   TEXT NOT NULL
);
CREATE TABLE note_asset_ref (      -- 引用关系，用于笔记删除时的资产 GC
  note_filepath TEXT NOT NULL,
  asset_id      TEXT NOT NULL,
  PRIMARY KEY (note_filepath, asset_id)
);
```

增量判定：

| 场景 | 行为 |
|---|---|
| md 变更、图片引用未变 | 重切分，image chunk 复用 vision 缓存（**零 VLM 调用**） |
| md 新增图片引用 | 只对新 asset 调 VLM |
| 本地图片文件被替换（sha256 变） | asset_id 变 → 新资产 → 调 VLM，旧资产 GC |
| 远程图 URL 不变但内容变 | HEAD 比对 ETag；无 ETag 则按 `image_remote_recheck_days`（默认 30）周期性重取 |
| 笔记删除 | 按 `note_asset_ref` 递减引用计数，归零则删缓存文件 |
| `status=pending/failed` | 下次 reindex 或 backfill 脚本重试 |

## 十四、风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| **VLM 幻觉** | 描述图中不存在的内容 → 检索假阳性 + 答案编造 | prompt 硬约束「只描述图中存在的」+ 上下文仅用于消歧 + `confidence` 字段 + 低置信度图在生成端降权 |
| **成本失控** | 500 张图 × 每张 1.5k token | 三级拦截：装饰图预判 → SVG 文本直取 → 内容哈希去重；预算护栏 + 缓存 + 异步 backfill |
| **隐私** | 笔记截图外发第三方 VLM | `image_allow_remote_fetch` + 总开关；建议敏感 vault 用本地 VLM（Ollama 的 `qwen2.5-vl` / `llava` 系列） |
| **远程图失效** | 链接挂了，缓存也没有 | 首次索引即下载落盘，之后不依赖原站；`missing` 状态可审计 |
| **SVG** | VLM 多数不吃 svg | 优先抽 `<text>`；需要视觉时用 `cairosvg` 栅格化（新增可选依赖） |
| **chunk 膨胀** | 内联摘要使 chunk 数上升 | 摘要限 50 字；实测影响 < 5% |
| **契约改名波及面** | `SourceInfo.type` → `origin` 影响 3 个模块 + 测试 | P0 一次性做完并跑全量回归，不留中间态 |
| **索引变慢** | 首次全量索引引入网络 IO + VLM | 图片处理与文本索引解耦，支持"先建索引后补图"；并发 + 预算上限 |

## 十五、关键设计决策记录（供 DECISIONS.md 摘录）

1. **资产主键用内容哈希而非路径** —— 跨笔记复用的图只理解一次；本地图被移动/重命名不触发重跑。
2. **VLM 输出结构化 JSON 而非一句 caption** —— `description` 喂 dense、`ocr_text` 喂 BM25、`summary_short` 内联正文，三者用途正交，合成一句会同时损失检索质量与生成质量。
3. **上下文进 prompt 但明令禁止污染 description** —— 只给消歧权，不给描述权，这是防幻觉的关键边界。
4. **双通道索引（内联 + 独立 chunk）而非二选一** —— 只内联则语义信息过短召不回；只独立 chunk 则正文在图片处出现语义断裂且无法渲染。
5. **image chunk 与文本 chunk 同池竞争** —— reranker 输入本就是文本，零改造；分池会引入融合排序的新问题。
6. **预计算 caption 为主、on-demand vision 为辅** —— 前者延迟与成本可控且可缓存，后者仅作为低置信度场景的兜底。
7. **总开关默认关闭** —— 与项目既有的 `structure_weight=0`、`agent_clarify_enabled` 等设计一致，保证任何时候可一键退回旧行为。
